CRITICAL FINDING — root cause identified from console logs
═══════════════════════════════════════════════════════════════
Confirmed via live browser console logs on the deployed admin panel:
two payment approvals for the same driver, 26 seconds apart, both
read almost the same base subscription_expires_at value and both
wrote the SAME final date (2026-08-06) instead of stacking. This is
a classic lost-update race condition, and it is 100% reproducible.

Root cause: the payment approval logic in the Admin Panel's
handleApprove function runs ENTIRELY in the FRONTEND (browser),
calling supabase.from(...) directly from the client:
  1. It SELECTs the driver's current subscription_expires_at
  2. It computes a new date in JavaScript
  3. It UPDATEs the row separately

This two-step (read-then-write) pattern can NEVER be made safe
against race conditions, no matter how the read logic is written —
there is always a time gap between step 1 and step 3 during which
a second approval can read the same stale value. This is true
regardless of how "correct" the read logic looks; the problem is
timing, not logic.

This also explains why all our previous backend fixes (atomic
GREATEST SQL, transactions, 409 idempotency guard in admin.ts)
never took effect for this flow — this frontend code never goes
through the backend API at all.

Additionally, the frontend code adds "+32 days" for a PAYMENT
approval, which is WRONG. 32 days is exclusive to the one-time
first-approval document gift — a completely separate action.
Payment approvals should add 30 days (or months * 30).
